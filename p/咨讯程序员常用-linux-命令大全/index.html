2.4 >、»、2>&1、tee、&&

写法 含义
command > out.log 标准输出写入文件，覆盖原内容
command >> out.log 标准输出追加到文件
command 2> err.log 标准错误写入文件
command > all.log 2>&1 标准输出和标准错误都写入 all.log
command 2>&1 | tee all.log 两种输出合并后，同时显示并保存；tee 默认覆盖
command | tee -a out.log 同时显示并追加标准输出
command < input.txt 从文件读取标准输入
command >/dev/null 2>&1 丢弃两种输出，排障时慎用
command1 && command2 前者成功才执行后者
command1 || command2 前者失败才执行后者
command1; command2 不论前者是否成功，都执行后者

重定向顺序有意义：command 2>&1 > out.log 会先让标准错误指向当时的标准输出，通常仍是终端，再单独重定向标准输出。

Bash 默认用管道最后一个命令的退出状态作为整个管道状态。脚本需要发现前面命令失败时，可使用 set -o pipefail；但 grep 未匹配返回 1，head 提前退出也可能使上游收到 SIGPIPE，需要结合具体流程处理。

3. 进程、线程与后台任务

3.1 找 PID 和查看进程

命令 用途
ps -ef 查看所有进程及父 PID、完整命令等
ps aux BSD 风格输出，包含 CPU、内存等；这里不写成 ps -aux
pgrep -af java 按完整命令行搜索进程
pgrep -ax java 精确匹配进程名 java，再显示命令行
ps -p 12345 -o pid,ppid,user,etime,%cpu,%mem,rss,vsz,args 查看一个进程的运行时间、CPU、内存和命令
ps -eo pid,ppid,stat,comm --forest 以树形方式显示进程关系
pstree -ap 12345 查看指定进程的子进程树，需安装 psmisc
top -p 12345 持续观察指定进程
top -H -p 12345 查看该进程内的线程
ps -L -p 12345 -o pid,tid,pcpu,stat,comm 列出线程 ID、CPU 与状态

top 中常用 P 按 CPU 排序、M 按内存排序、1 切换各 CPU 核心显示、q 退出。ps %CPU 通常是进程整个生存期的平均比例，top 更适合观察当前采样区间；多线程进程可能超过 100%。

常见进程状态：R 正在运行或可运行、S 可中断睡眠、D 不可中断睡眠（常与 I/O 等待有关）、T 停止、Z 僵尸。僵尸进程已经退出，需要父进程回收其状态，继续对它 kill -9 无法解决。

4. Linux 系统资源：磁盘、内存、CPU 与 I/O

4.1 df -h：文件系统空间，du：目录占用

命令 用途
df -h 查看各文件系统的容量、已用、可用和使用率
df -h /srv/app 查看这个路径所在的文件系统
df -i 查看 inode 使用率，大量小文件可能把 inode 用尽
du -sh /srv/app 统计目录总占用，扫描大目录可能较慢
du -xhd1 /srv/app | sort -h 查看下一层目录的占用，限制在同一文件系统
lsblk -f 查看块设备、文件系统和挂载点
findmnt /srv/app 查看路径对应的挂载信息
sudo lsof +L1 查找已删除但仍被进程打开的文件

df -h 查的是磁盘空间，不是 RAM。 df 是文件系统视角，du 是扫描目录树的视角，因此两者不一定相等。常见原因包括已删除但未关闭的文件、挂载点遮住的内容、文件系统元数据和权限不足。

磁盘满时先定位目录和大文件，再决定轮转、归档或释放。直接删除进程仍打开的日志，空间可能要等进程关闭该文件后才真正释放。

# 所有进程：RSS 从大到小；RSS、VSZ 通常以 KiB 显示

ps -p 12345 -o rss= | awk '{printf "RSS: %.1f MiB\n", $1/1024}'
指标 含义 排查时怎么用
RSS / RES 当前驻留在物理内存中的页，包含共享页 找占用大的进程、观察趋势；逐进程相加会重复计算共享部分
VSZ / VIRT 虚拟地址空间大小 可能包含尚未驻留的映射或预留空间，不能等同实际 RAM
%MEM 通常按 RSS 占机器物理内存比例计算 容器里可能不反映该容器的 limit
PSS 将共享页按共享进程数量分摊后的占用 比较多个进程的实际分摊占用
USS 进程独占的驻留内存，常由工具根据私有页汇总 判断独占占用，具体口径应看工具说明
JVM heap used JVM 堆里已使用的空间 判断 Java 对象占用，还要观察 GC 后存活量

RSS 不是 Java heap。 一个进程还可能包含线程栈、Metaspace、JIT 代码、直接内存、native 库、文件映射及共享内存等。ps 与 /proc/PID/status 的部分内存计数是近似值，进一步核对可读 smaps_rollup。

4.5 CPU、负载与 I/O

命令 用途与解读
top 实时看 CPU、内存和进程
htop 交互式进程查看器，需要额外安装
uptime 运行时间与最近 1、5、15 分钟 load average
nproc 当前进程可用的处理单元数量；容器配额需额外核对
lscpu CPU 架构、核心与线程信息
vmstat 1 10 每秒采样一次，共 10 次；常看 r、b、si、so、wa
pidstat -p 12345 -u -r -d 1 10 按进程采样 CPU、内存、I/O，来自 sysstat
iostat -xz 1 10 查看设备吞吐、延迟与队列，来自 sysstat
mpstat -P ALL 1 10 每个 CPU 的使用率，来自 sysstat

6. 实战分类：如何排查 memory leak

6.1 第一步：先分清“哪一种内存问题”

现象 先看什么 下一步
系统 available 持续降低 free -h、RSS 排名、cgroup 判断是哪一个进程、文件缓存或组内占用增长
单进程 RSS 持续上涨 ps、smaps_rollup、heap 区分堆内对象、匿名页、映射和共享页
Java heap GC 后基线持续上涨 jstat、GC 日志、业务负载 对象直方图、heap dump 与引用链
heap 稳定但 RSS 上涨 NMT、线程数、BufferPool、pmap 检查 native、线程栈、直接内存、映射
OutOfMemoryError: Java heap space 堆限制、存活对象、瞬时分配 可能是泄漏，也可能是负载或堆容量不足
OutOfMemoryError: Metaspace 类数量、类加载器、Metaspace 检查动态类生成、热部署和类加载器释放
unable to create native thread 线程数、用户限制、cgroup pids、内存 不应只增加 Xmx；更大堆还可能挤压 native 空间
Direct buffer memory BufferPool、直接内存限制、缓冲区生命周期 排查缓冲区积压与回收
容器 OOMKilled，无 Java OOM 容器限制、memory.events、平台日志 核对整个 cgroup 总占用和峰值
df -h 满或日志无法写入 磁盘与 inode 属于存储问题，可能同时影响 dump 和日志留存

下面脚本只采集进程内存快照，不主动触发 GC。示例持续约 10 分钟，每 10 秒一次，保存到一个新日志文件：

#!/usr/bin/env bash
pid=12345
out="memory-${pid}-$(date +%Y%m%d-%H%M%S).log"

for ((i=0; i<60; i++)); do
  # 进程退出就结束；采样期间也应留意 PID 被重用的可能
  if ! ps -p "$pid" >/dev/null; then
    break
  fi
  {
    date -Is
    ps -p "$pid" -o pid,etime,%cpu,%mem,rss,vsz,nlwp,args
    grep -E 'VmRSS|VmSwap|RssAnon|RssFile|Threads' "/proc/$pid/status"

  } >> "$out"
  sleep 10
done

6.3 第三步：按证据深入

  1. GC 后存活量增长：在相近业务状态下采集两个时间点的对象分布，必要时获得 dump，找被长期持有的集合、缓存、队列、ThreadLocal 或类加载器引用。
  2. 线程数增长：比较线程栈，检查每次请求创建线程、线程池无上限、任务堵塞等情况；线程栈也消耗 native 内存。
  3. heap 稳定，匿名 RSS 增长：结合 NMT 差值、BufferPool、native 分配工具和库行为调查。NMT 未能解释的增长仍可能来自 native 库或分配器保留内存。
  4. 文件映射／缓存增长：检查 mmap、大文件访问和容器 memory.stat；进程 RSS、cgroup 文件缓存与 heap 的口径不同。
  5. 修复后重复同一工作负载：确认内存随负载进入稳定区间，GC 后基线不再持续抬升，而不是只看重启后降下来了。

“GC 后没有立即归还操作系统”“RSS 高于 Xmx”“缓存增长”都不能单独证明泄漏。对象长期无用却仍被引用、native 分配未释放等，需要通过时间趋势与保留链或分配证据确认。也不要为了观察而反复执行 jcmd PID GC.run；主动 GC 会改变现场并可能造成停顿。

14.2 strace、perf、native 泄漏工具

命令 用途与成本
sudo strace -f -tt -T -p 12345 -o trace-01.log 跟踪系统调用，Ctrl + C 结束附加；可能明显拖慢目标，日志增长快
